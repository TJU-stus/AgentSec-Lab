## 1. 项目一句话

做一个「AI 助手安全实验平台」：网页上创建 AI 助手（Agent）、配工具、执行任务，把每一步行动都记成流水账——为以后研究「攻击 AI 助手 / 保护 AI 助手」备好实验场地。

## 2. 总体分层图

```
网页平台 Platform（页面 + 数据）            ← 成员3 负责
        │ ① 用户输入任务 / ② 拿回结果和记录
        ▼
运行调度器 Runner（中转站 + 记录汇总）      ← 成员2 负责
        │ ③ 转任务（流式方式）
        ▼
Agent 大脑 Dify（决定怎么做）               ← 成员2 部署与配置
        │ ④ 决定调用工具
        ▼
工具网关 Gateway（工具守门员）              ← 成员2 负责
        │ ⑤ 放行 → 执行
        ▼
工具 calculator（计算器）                   ← 成员2 负责
        │
        ▼
共享记录模块 common/trace.py               ← 成员1 负责，所有人调用
```

## 3. 各层职责

| 层 | 负责成员 | 职责（大白话） | 关键点 |
| --- | --- | --- | --- |
| 网页平台 | 成员3 | 用户看到的页面 + 数据存取 | 不直接面对 Dify，只和 Runner 说话 |
| 运行调度器 Runner | 成员2 | 接住任务 → 转给 Dify → 收过程 → 汇总成记录 | 调用 Dify 必须用**流式**方式，才能拿到中间过程 |
| Agent 大脑 Dify | 成员2 | 听懂任务、决定要不要调用工具 | 配置导出备份，版本锁定 |
| 工具网关 Gateway | 成员2 | 所有工具调用的唯一入口 | 现在管 calculator，以后做权限、拦截 |
| 工具 calculator | 成员2 | 算两个数的和 | 禁止 eval()，只认数字和运算符 |
| 共享记录模块 | 成员1 | 记录格式的唯一标准（代码实现） | 别人 import 调用，不各自造格式 |

## 5. 接口约定（本文件最重要的部分）

规则：**改接口必须三方都同意**；接口定义以本文件为准，代码实现以接口为准。

### 5.1 平台 → Runner（成员3 调成员2）

| 项目 | 内容 |
| --- | --- |
| 方式 | HTTP 请求 |
| 传什么 | 任务文字（如「计算 123+456」）+ 用哪个 Agent |
| 收什么 | run_id（本次运行编号）、最终回答、本次运行的全部记录 |
| 状态 | 待成员2 给出具体地址与字段名（见第 10 节） |

### 5.2 Runner → Dify（成员2 调 Dify）

| 项目 | 内容 |
| --- | --- |
| 方式 | Dify 的接口调用，**流式返回** |
| 传什么 | 用户任务（按 Dify App 的输入格式） |
| 收什么 | 流式事件：Agent 的中间想法、想调的工具、最终回答 |
| 状态 | 具体事件字段等成员2 完成「可行性小验证」后回填（见第 10 节） |

### 5.3 Agent（经 Runner）→ Gateway（成员2 内部）

| 项目 | 内容 |
| --- | --- |
| 方式 | HTTP 请求（Dify 里配成 HTTP 工具，指向网关地址） |
| 传什么 | run_id、工具名、参数 |
| 收什么 | 成功结果，或明确拒绝的错误提示 |
| 现状 | 只有 calculator：POST /tools/calculator，传 {"a": 1, "b": 2}，收 {"result": 3} |

### 5.4 记录格式（成员2、3 调成员1）

- 唯一标准：common/trace.py（成员1 写，先于其他人使用前提供第一版）
- 一行记录五字段：run_id / timestamp / event_type / source / data
- 四类事件：agent_tool_attempted（Agent 想调工具）、gateway_policy_decision（放行 allow / 拒绝 deny）、tool_executed（执行了）、tool_result（返回了）

## 6. 一次完整运行长什么样（文字版流程）

1. 用户在网页输入「计算 123+456」，点运行；
2. 平台生成一个 run_id，把任务交给 Runner；
3. Runner 用流式方式把任务转给 Dify；
4. Dify 的 Agent 决定调用计算器工具（产生 agent_tool_attempted 事件）；
5. Runner 把工具调用发给 Gateway（Gateway 记 gateway_policy_decision 事件，第一版一律放行）；
6. Gateway 执行 calculator（tool_executed 事件），拿回结果（tool_result 事件）交回 Dify；
7. Dify 组织最终回答，流式结束；
8. Runner 把最终回答 + 全部记录按 common/trace.py 的格式整理好，交回平台；
9. 平台把记录存进数据库（runs 表 + trace_events 表），页面展示结果和记录。

## 7. 设计原则（为什么这么分层）

1. **Dify 负责聪明，自研代码负责安全**：Dify 只当大脑；权限、拦截、记录都长在我们的代码里，可 review、可版本化。
2. **记录是项目的地基**：从第一天起，每一步动作都按 common/trace.py 记下来。以后做攻击分析，靠的就是这些记录。
3. **中间过程必须拿到**：所以 Runner 用流式调用 Dify——拿不到「Agent 想调什么工具」，以后就没法分析攻击意图。
4. **先简单后复杂**：第一阶段只有 calculator 一个工具、权限全放行、不做攻击。但结构上把位置留好（网关、记录模块），第二阶段直接往上加东西，不大改。

## 8. 第一阶段明确不做

- 诱导攻击实验与攻击用例库
- 多 Agent、RAG、MCP 等扩展
- 自动攻击脚本
- 复杂权限系统（网关只做基础参数校验）

## 9. 第一阶段验收（详见《第一阶段任务分配指导书》第 9 节）

- Dify 能跑、Runner 能中转、计算器通过成员1 的捣乱用例集（≥30 条）
- 页面输入「计算 123+456」返回 579
- 一次运行的记录完整保存且能被校验
- tests/mvp_check.py 一条命令输出「通过 N / 未通过 M」
